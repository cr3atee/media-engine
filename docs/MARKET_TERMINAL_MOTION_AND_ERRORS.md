# Market Terminal: анимации, ошибки и журнал диагностики

Дата: 23 октября 2026 года. Обновлено 30 октября 2026 года.
Статус: базовый пакет 5A реализован; оставшиеся ограничения перечислены ниже.

## 1. Приоритет

Плавность и скорость относятся к базовому качеству интерфейса. Ошибки и
переходы проектируются одновременно с обычными экранами, а не после их вёрстки.
Пользователь должен сразу видеть реакцию на действие, понимать результат и
иметь возможность продолжить работу после сбоя.

Новые требования: полноценные 404, единое представление непредвиденной ошибки,
долговременное сохранение диагностики на backend и просмотр с административными
правами. Серверная часть журнала является отдельной задачей реализации внутри
этого расширения плана; оформление страницы само по себе её не создаёт.

## 3. Наша система движения

### Базовые параметры

| Параметр | Начальное значение | Использование |
| --- | --- | --- |
| `motion-press` | 80 мс | Реакция на нажатие |
| `motion-fast` | 150 мс | Меню, переключатель, небольшое изменение |
| `motion-panel` | 220 мс | Диалог, раскрытие панели |
| `motion-page` | 280 мс | Каталог → товар и возврат |
| `ease-control` | `cubic-bezier(0.2, 0, 0.2, 1)` | Локальные контролы |
| `ease-page` | `cubic-bezier(0.25, 1, 0.5, 1)` | Переходы между экранами |

Реакция на ввод начинается в ближайшем доступном кадре. Длительность анимации
не является задержкой перед обработкой клика или отправкой запроса.

### Поведение компонентов

| Событие | Движение | Длительность и ограничения |
| --- | --- | --- |
| Нажатие кнопки | Изменение поверхности; допустим scale 0.98 | 80 мс на нажатие, до 150 мс на возврат; геометрия окружения не меняется |
| Hover карточки | Подсветка и смещение изображения до 2px | 120–150 мс, только на устройствах с hover; текст не прыгает |
| Открытие меню | Opacity + scale 0.96 → 1 от точки кнопки | 150–180 мс; закрытие 100–150 мс; не уменьшать читаемость длинного меню |
| Активная категория | Перемещение подчёркивания | 150–180 мс; фильтрация начинается сразу |
| Каталог → товар | Сдвиг 16–24px + opacity у содержимого; шапка остаётся | 240–280 мс; возврат в противоположном направлении |
| Мобильная панель | Короткое движение по направлению открытия + opacity | 240–300 мс; без обязательного пролёта через всю ширину экрана |
| Диалог | Сдвиг 8px + opacity; отдельно затемнение | 180–220 мс; без прыжков и повторного отскока |
| Обновление поиска | Данные заменяются сразу по готовности, мягкое появление | 120–160 мс; нет последовательного появления всех 50 карточек |
| Успех действия | Галочка/текст и локальное появление | 150–180 мс после подтверждения сервера |
| Ошибка | Спокойное появление рядом с проблемой | 120–160 мс; без тряски всей формы и красных вспышек |
| Изображение загрузилось | Fade внутри уже занятого квадратного места | 120–180 мс; нулевой сдвиг сетки |
| Обновление цены | Смена значения и краткая локальная подсветка | До 200 мс; без счётчика, показывающего промежуточные выдуманные цены |

Не анимировать всю страницу при каждом ответе API. Не задерживать отображение
готового результата ради минимальной длительности spinner. Если ответ пришёл
быстро, достаточно мгновенного pressed-состояния. Индикатор долгой загрузки
может появиться после 150 мс, но сам запрос начинается сразу.

Повторное открытие/закрытие, Back во время перехода и смена категории до
завершения предыдущего движения приводят к последнему запрошенному состоянию.
Не накапливать очередь анимаций. Отменённый переход освобождает listeners,
таймеры и временные слои. Фокус и видимость старого экрана не зависят только
от события `transitionend`, которое может не прийти.

### Производительность

- Основные анимации выполняются через `transform` и `opacity`.
- Не анимировать `width`, `height`, `top`, `left` у длинных списков или большие blur-фильтры.
- Не использовать `transition: all` для универсальных компонентов.
- DOM-измерения и изменения разделяются; не измерять каждую карточку в каждом кадре.
- `will-change` включается лишь для действительно анимируемых элементов и снимается.
- Изображения имеют зарезервированное место; шрифт не вызывает повторную перестройку экрана.
- Сеть, логирование и тяжёлая обработка данных не привязаны к кадрам анимации.
- CSS transitions и Web Animations API достаточны для первого варианта; отдельная
  тяжёлая библиотека и анимированные стикеры не являются условием плавности.

Цель: ровный отклик на обычном ноутбуке и телефоне. При 60 Гц бюджет кадра
около 16.7 мс, при 120 Гц около 8.3 мс. Это ориентиры профилирования, не
обещание одинакового FPS на любом устройстве. Проверять запись Performance
с реальными изображениями и 50 карточками, включая замедление CPU.

При `prefers-reduced-motion` убрать перемещения, масштабирование, плавную
прокрутку и декоративные анимации. Мгновенная смена состояния либо короткий
fade до 80 мс сохраняют обратную связь. Не оставлять скрытые элементы или
заблокированные кнопки из-за нулевой длительности.

### Реализованный переход между страницами

Рабочие `/terminal`, `/terminal/review`, HTML 404 и безопасная error page
используют один CSP-совместимый переход без внешней библиотеки. До готовности
начального состояния прямые дочерние элементы страницы скрыты, поверх них
показан непрозрачный фон и центральный SVG-знак Market Terminal. Каталог и
кабинет сами снимают экран после завершения своей начальной async-загрузки;
для ошибок и 404 достаточно события `load`. Пятисекундный аварийный таймер не
позволяет интерфейсу навсегда остаться заблокированным при сбое инициализации.

Внутренние GET-переходы в пределах `/terminal` показывают тот же слой до смены
документа. SPA-поиск, карточки товара и формы со своей обработкой не
перехватываются повторно. BFCache восстанавливается без зависшего слоя.
`prefers-reduced-motion` отключает прорисовку и пульсацию знака, а отсутствие
JavaScript не скрывает содержимое. Browser verifier подтвердил снятие начального
слоя и видимый непрозрачный слой в момент внутренней навигации.

## 4. Единый язык ошибок

У непредвиденных сбоев одно узнаваемое сообщение:

> Не удалось выполнить действие.
> Попробуйте ещё раз. Если ошибка повторится, передайте код ошибки поддержке.

Ниже: «Повторить», подходящий выход («В каталог» или «Закрыть») и
«Код ошибки: …» с кнопкой копирования, если идентификатор доступен.
Для ошибки чтения можно добавить конкретный контекст: «Не удалось загрузить
предложения». Не выводить пользователю SQL, traceback или необработанный текст
исключения. Текст «Ошибка уже отправлена» допустим только после подтверждённого
приёма отчёта, а не по самому факту показа сообщения.

Единство означает общую структуру, тон и поведение. Ошибки проверки формы,
истёкшая сессия и 404 получают полезное специфическое объяснение.

| Состояние | Заголовок / смысл | Действие |
| --- | --- | --- |
| Неизвестный адрес страницы | «Страница не найдена»; возможно, адрес устарел | «В каталог», «Назад» при наличии предыдущего экрана |
| Товар отсутствует | «Товар не найден»; ссылка могла устареть | Поиск или каталог; не утверждать без данных, что товар продан |
| 500 / неизвестный сбой | Общее сообщение непредвиденной ошибки | Безопасный повтор, код диагностики |
| Сеть недоступна / timeout | «Не удалось связаться с сервером» | Повторить; не обещать доставку отчёта |
| 503 / обслуживание | «Сервис временно недоступен» | Повторить; без выдуманного времени восстановления |
| 401 | «Сессия завершилась. Войдите снова» | Сохранить черновик в пределах текущей вкладки и показать вход |
| 403 | «Недостаточно прав для этого действия» | Вернуться; не предлагать обход роли |
| 409 | «Данные изменились. Обновите запись» | Обновить и проверить решение заново |
| 422 | Конкретная проблема поля | Ошибка рядом с полем, фокус на нём |
| 429 | «Слишком много запросов. Подождите немного» | Учитывать серверный `Retry-After`, если передан |

Повтор GET безопасен. Для изменения каталога после timeout нельзя слепо
создавать новую операцию: исход мог остаться неизвестен. Сохраняются существующая
idempotency key, проверка состояния и явное подтверждение после конфликтов.

### Страницы 404 и глобальный fallback

404 оформляется в общей тёмной системе: компактный знак/иллюстрация, читаемый
заголовок, краткий текст и заметный выход. Никакой огромной надписи 404 на весь
экран, бесконечного мультфильма или автоматического редиректа с потерей адреса.

Неизвестный документ под `/terminal/...` при GET/HEAD должен вернуть настоящий
HTTP `404` и HTML-страницу. API `/api/...` продолжает возвращать JSON и корректный
статус. Отсутствующий CSS/JS не должен получать HTML с кодом `200`. Catch-all
маршрут не перехватывает действующие API и ассеты.

Если `/terminal?product=...` загрузил оболочку с `200`, а запрос товара вернул
`404`, UI показывает «Товар не найден»; не утверждать, что HTTP-статус уже
загруженного документа изменился. Прямая адресация отдельного SSR-документа
позднее потребует собственного серверного решения.

Если сломан сам frontend или не загрузился JS, минимальный fallback и ссылка
в каталог должны работать без зависимости от неисправного компонента.
Если упала БД, страница 500 не должна обращаться к ней ради своего отображения.

404 на внешней площадке отличается от нашей 404. Браузер не может надёжно
проверять произвольные чужие страницы из-за ограничений доступа. Не объявлять
все внешние ссылки проверенными автоматически и не перехватывать чужую страницу.

## 5. Что реализовано в MediaEngine

- `app/api/errors.py`: общий JSON-конверт `error.code/message/details/request_id`;
  неожиданный 500 дополнительно получает incident ID и сохраняется отдельно от
  неуспешной бизнес-транзакции.
- `app/api/correlation.py`: ограниченный по формату request ID, состояние запроса,
  `X-Request-ID` и привязка контекста.
- PostgreSQL revision `0019_diagnostic_incidents`, memory/PostgreSQL repository
  implementations и `DiagnosticService` сохраняют очищенные агрегаты с
  fingerprint, first/last seen и счётчиком повторов. Retention по умолчанию —
  30 дней.
- При отказе основной БД сервис пишет ограниченный ротируемый JSONL в
  `DIAGNOSTICS_FALLBACK_PATH`. Compose монтирует для него отдельный постоянный
  volume; локальный `var/` исключён из Git.
- Неизвестный документ `/terminal/...` возвращает настоящую HTML-страницу со
  статусом `404`; отсутствующий asset не получает HTML, а `/api/...` сохраняет
  JSON-контракт.
- Неожиданный terminal 500 получает автономный HTML fallback с incident/request
  ID. Страница не обращается к БД для собственного отображения.
- Аутентифицированный кабинет отправляет только allowlisted frontend metadata;
  сообщения, stack, DOM и значения форм не принимаются. Повторы ограничены в
  браузере и на процессе backend, а сбой reporting endpoint не репортит себя.
- Экран «Журнал ошибок» доступен только текущей продуктовой роли `admin`,
  подтверждённой сервером. Tenant owner/administrator такого права не получает.

Переиспользовать конверт и correlation middleware. Не вводить вторую независимую
систему бизнес-ошибок или переписывать существующие repository/workflow контракты.

## 6. Куда сохранять ошибки

Проектное решение: хранение на backend, административный аккаунт получает
доступ к просмотру. Сам аккаунт не является местом хранения и не должен
получать отдельное сообщение на каждую повторяющуюся ошибку.

### Сохранение

Основной журнал диагностических инцидентов сохраняется в PostgreSQL через
отдельную техническую границу, вне транзакции бизнес-действия. Ошибка и rollback
операции не должны уничтожать диагностическую запись, а сохранение журнала
не должно превращать rollback в commit.

При недоступности PostgreSQL: ограниченный по размеру структурированный JSONL
журнал на постоянном backend volume, вне web-root, с ротацией. Это не файл
внутри временного контейнера и не только строка в консоли. Сбой записи журнала
не запускает рекурсивное логирование самого себя и не блокирует ответ пользователю.

После восстановления можно доставить резервные записи в основной журнал с
дедупликацией по ID события. До доставки админ-экран не утверждает, что видит
все ошибки. Ограничения диска, права и поведение при заполнении проверяются.

Начальный срок хранения: 30 дней, настраиваемый; общий размер и число событий
ограничены. Финальные лимиты фиксируются при реализации на основании окружения.
Не добавлять внешнюю аналитику или новый SaaS только ради этой задачи.

### Содержимое записи

| Поле | Правило |
| --- | --- |
| Incident ID, время UTC, версия приложения, окружение | Создаются/проверяются сервером |
| Источник | Backend или frontend; клиентские данные помечаются как недоверенные |
| Код, уровень, компонент, действие | Ограниченный словарь; ожидаемая 404 не равна аварии 500 |
| Request ID | Корреляция с существующим API; это не ключ доступа и не надёжный уникальный ID инцидента |
| Маршрут, метод, HTTP-статус | Шаблон пути без query, токенов и произвольных URL |
| Tenant/user ID при наличии | Только из проверенного серверного контекста |
| Тип ошибки, безопасные stack frames | После очистки; не сохранять locals или тела запроса |
| Fingerprint, first/last seen, счётчик повторов | Группировать одинаковые сбои и ограничивать шум |

Не сохранять пароли, auth headers, cookies, access/refresh tokens, API keys,
полный DOM, значения полей форм, содержимое localStorage и полные тела ответов.
Сообщения исключений и URL также проходят очистку: секрет может находиться в
тексте traceback, а не только в явно названном поле. Нынешний безопасный ответ
API не является доказательством, что любой серверный traceback уже очищен.

### Ошибки браузера

Будущий обработчик покрывает `error`, `unhandledrejection` и известные сбои
загрузки/отрисовки. Отправляется минимальный структурированный отчёт через
same-origin endpoint: component/action, release, код ошибки и request ID,
если он действительно получен. Клиент не назначает себе tenant или admin роль.

Отправка ограничена размером, частотой и timeout; одинаковые ошибки объединяются.
Сбой самого reporting endpoint не порождает новый отчёт о себе. При offline
возможен небольшой буфер в памяти вкладки; не отправлять бесконечно и не
обещать сохранность после закрытия браузера. Для гостевого приёмника нужны
серверные ограничения нагрузки и проверка входной структуры.

Для 500, уже записанного backend, браузерный отчёт связывается с ним, а не
увеличивает счётчик независимых аварий. Подтверждение приёма содержит incident ID;
только после него можно показывать «Ошибка передана».

## 7. Административный просмотр

Экран «Журнал ошибок»: время, источник, действие, статус, число повторов,
код обращения. Фильтры: период, окружение, компонент, уровень. Детали
содержат очищенную диагностику и связанные request IDs. Нужны пагинация и
индексы по времени/области доступа; не читать весь журнал в браузер.

Доступ следует четырём продуктовым ролям из
[плана интерфейса, раздел 4](MARKET_TERMINAL_INTERFACE_REBUILD.md): пользователь,
партнёр, модератор, админ. Полный очищенный технический журнал доступен только
админу с явным серверным полномочием. Пользователь видит код своей ошибки,
партнёр дополнительно безопасное состояние собственных операций, модератор
контекст ошибки своей проверки; эти представления не раскрывают traceback.

Существующий tenant administrator/owner не получает глобальный журнал из-за
названия роли. Гостевые/непривязанные инциденты относятся к глобальной области.
В существующем коде есть key-based admin boundary, но секретный административный
API key нельзя встраивать в клиентский JavaScript.

Перед реализацией страницы связать доступ с имеющимися серверными проверками
аутентификации/прав. Если для browser account глобального доступа ещё нет,
это явная задача авторизации, а не скрытая кнопка с доверенной ролью в браузере.
Чтение и экспорт диагностических данных должны иметь проверяемый аудит.

## 9. Порядок включения в общую перестройку

1. В пакет макетов добавить 404, глобальный сбой, локальную ошибку формы и
   интерактивную демонстрацию движения. Статичный скриншот не проверяет анимацию.
2. В общую оболочку включить motion tokens, сообщения, fallback и сохранение
   request ID на клиенте. Проверить навигацию и reduced motion до масштабирования.
3. Реализовать журнал отдельно от бизнес-процессинга: persistence, резервное
   сохранение, очистку данных, приём frontend-отчётов и правила доступа.
4. Подключить административный просмотр и проверить реальный поиск ошибки по коду.
5. На общей приёмке пройти обычный сценарий и сценарии с преднамеренными сбоями
   в изолированном тестовом окружении. Рабочие решения каталога не изменять.

## 10. Фактическая проверка пакета 5A

27 октября 2026 года изолированный PostgreSQL 17 прошёл clean upgrade до
`0019_diagnostic_incidents`, `alembic current` и `alembic check`. Конкурентная
проверка восьми одинаковых backend-сбоев создала один агрегат со счётчиком `8`;
тот же incident прочитан после пересоздания engine/session. Memory и API тесты
подтвердили дедупликацию, запрет чтения обычным пользователем, безопасный 500,
HTML/JSON 404 и ротируемый fallback без текста исключения.

Повторный запуск PostgreSQL verifier на той же тестовой базе также прошёл:
идемпотентная проверка не требует очистки сохранённых пользователей или
инцидентов. Alembic прошёл downgrade до `0018_product_roles`, повторный upgrade
до head, `current`, `check` и offline SQL. Полный Pytest: `605 passed`,
`60 skipped`; MyPy: `479` файлов без ошибок; Ruff и Ruff format для всех
затронутых Python-файлов прошли.

Ограничения текущей итерации: fallback JSONL не импортируется автоматически
обратно в PostgreSQL; чтение журнала ещё не создаёт отдельную audit-запись;
frontend reporting включён только в аутентифицированном кабинете; rate limit
координируется на уровне процесса и должен дополняться gateway-limit в
многоузловом production. Проверка движения/FPS остаётся частью общей приёмки UI.
